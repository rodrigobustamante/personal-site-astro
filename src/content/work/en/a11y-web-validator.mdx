<Section label="01 — Problem & Context" title="Accessibility checks people actually run">

Most accessibility problems are found late, by the people who run into them. Automated checks don't replace a manual audit, but they catch a large share of the common failures: missing alternative text, low contrast, unlabelled controls, broken heading order. A11yScan makes that first pass take a few seconds. You paste a URL, the page is loaded in a real browser, and you get the violations grouped by impact, the exact HTML that causes each one, and a link to how to fix it.

It's a side project, built on my own as a pnpm monorepo: a Next.js front end, an Express API that drives the browser, and a shared types package between them.

</Section>

<Section label="02 — Architecture" title="A real browser behind a small API">
  <Pillars>
    <Pillar title="Rules run where the page renders">

The API opens the URL in headless Chromium with Playwright and runs axe-core against the rendered DOM, with the WCAG 2.0 and 2.1 A/AA rule sets plus axe's best practices. Running in a browser matters: contrast, focus and ARIA problems often only exist after scripts and styles have run. To keep scans fast, images, fonts and media are not downloaded, while stylesheets are, so contrast is measured on the real colours.

    </Pillar>
    <Pillar title="A score and a report">

Each violation is weighted by impact and by how many elements it affects, and the result becomes a 0–100 health score that is easy to track over time. The front end, built on Radix UI primitives, groups issues by severity and shows the offending HTML for each one. Results can be exported as a PDF report, rendered on the server from the same data.

    </Pillar>

  </Pillars>
</Section>

<Section label="03 — Differentiator" title="A scanner that can't be turned inward" highlight>

A service that loads any URL a stranger gives it is an easy target for server-side request forgery: point it at `localhost`, a private network or a cloud metadata address, and the report hands back whatever it finds. Before making the repository public I treated that as the main risk.

A first guard that checked every request the browser made was not enough: Playwright doesn't intercept the individual hops of an HTTP redirect, so a public URL that redirected to an internal address went through, and I reproduced the leak locally. The fix moves the check to the network boundary. Chromium now sends all its traffic through a small egress proxy inside the API, which resolves each destination, refuses private and reserved IPv4 and IPv6 ranges, and connects to the exact address it checked. That closes redirects, DNS rebinding and WebSockets in one place, with the per-request guard kept as a second layer.

The PDF export got the same treatment: the report data is validated, every value is escaped, and the page is rendered with JavaScript and network access turned off. A limit on concurrent browsers keeps a burst of requests from taking the service down.

</Section>
